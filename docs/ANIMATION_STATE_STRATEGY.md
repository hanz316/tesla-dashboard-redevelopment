# 动画状态策略（A/B/C/D 分类）

为什么不是"所有状态都做成 30fps 长动画"：设备是 2×Cortex-A7 纯 CPU 光栅，
可用 RAM ≈183MB，30fps 下每帧预算 33.3ms。一次 356×236 的 PNG 解码在设备
上约 6.9ms（≈21% 帧预算，实测换算见 `RENDERING_CAPABILITY_AUDIT.md` 第 11 节）。
因此必须按"变化频率 × 视觉收益 × 解码成本"分类，而不是统一做视频式动画。

| 类别 | 定义 | 典型元素 | 实现方式 | 成本 |
|---|---|---|---|---|
| **A. Continuous Frame Animation** | 用户动作触发的短动画，播放一次后停在末态 | 车门、前备箱、后备箱 | Blender 预渲染透明 PNG 序列，`mode: to_state` | 16 帧 = 5.1MB 解码上限；**只在过渡瞬间解码** |
| **B. Static Overlay** | 只有开/关两态，无中间过程 | 刹车灯、大灯 | 单帧 PNG 叠加（`overlays`）| 1 帧 = 0.32MB，可常驻 |
| **C. Short Loop** | 周期性重复的短循环 | 左/右转向灯、双闪 | 12 帧循环序列（`mode: loop`）+ `fps` 控制 | 12 帧 = 3.85MB；循环播放解码占用 CPU，需限速 |
| **D. Runtime Vector Animation** | 连续变化、参数化、不需要帧序列 | AP 走廊、盲区辉光、警告脉冲、能量弧、进度条 | **NanoVG/AGG 运行时矢量绘制**（或圆角矩形进度）| 无解码成本，只有光栅化成本 |

## 分类判据

1. **是否有明确的离散中间形态？**
   有（门的铰链角度）→ A；无（亮度/长度连续变化）→ D。
2. **状态是否只有两态？**
   是 → B（便宜且像素完美）。
3. **是否需要周期性重复？**
   是 → C（但要限制 fps：转向灯用 12fps 足够，30fps 纯属浪费）。
4. **是否由实时信号连续驱动？**
   是 → D（用矢量，避免为无限中间态渲染帧）。

## 约束（硬性）

- 同一时刻**最多 1–2 个**帧序列动画在播放（解码预算 21%/个）
- 循环动画（C）限制在 12fps，除非实测有余量
- A 类动画播放结束后立即释放解码缓冲，只保留末帧
- D 类**不产生任何 PNG**；如果某元素能用矢量表达就不要渲染帧
- 所有序列必须通过 `tools/assets/check_budget.py` 与
  `tools/assets/verify_alignment.py`

## 为什么门用 A 而不是 D

门的开合是**有限离散过程**（0→55°），预渲染能保留正确的透视、遮蔽与光照
（实时矢量做不到），而且只在用户开门/关门的几秒内解码。这是"视觉质量优先、
成本可预测"的取舍。

## 为什么转向灯用 C 而不是 D

转向灯是纯色发光体，理论上 D 更省，但 C 只多 12 帧且视觉（含灯罩辉光）
更真实；代价被 12fps + 12 帧上限控制住。

## 为什么 AP 走廊/盲区用 D 而不是 A

它们的形状随车速/目标数连续变化，用帧序列等于为无限状态渲染，成本不可控；
矢量绘制每次只画几条曲线，几乎零额外内存。
