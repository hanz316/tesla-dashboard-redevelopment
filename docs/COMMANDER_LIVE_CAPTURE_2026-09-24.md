# 指挥官模块实机采集（2026-09-24，车静止）

状态：**已在真实模块上完成被动采集；原始证据在本地，未提交。**

本轮没有做任何车辆动作：没有挂挡、没有踩加速踏板、没有反复开关车门/前后备箱，
也没有向原车 UART 发任何东西。仪表本身没有参与——用一台 Mac 作为 BLE 中心，
直接对模块做**只读查询**。

## 1. 为什么是 Mac 采集

```text
仪表（T113）  ：平台未开放通用 GATT client，做不了 BLE 中心
手机小程序     ：是 BLE 中心，但被占住时模块停止广播，且小程序不方便做原始取证
Mac（本次）    ：自带 BLE 中心能力 → 直连模块 FFF0/FFF1，抓原始帧
         用法：python3 tools/device/commander_ble_capture.py --address <uuid> --seconds 32
```

设备：广播名 `TSL6`，地址 `AE779A7D-2BFD-2684-BE79-F85D8CBE8604`（macOS 的
CoreBluetooth 句柄），RSSI −60 dBm，广播含服务 `0000fff0-...`。
FFF1 属性：`write` / `write-without-response` / `notify`。

安全边界（脚本硬编码，非口头承诺）：

* 只发查询：160、176、208、209、210（193 已分类但未用）。
* **167 在脚本里不存在**，写入前 `assert_query()` 断言白名单。
* 唯一的非查询写入是模块自己的密码握手（见 §3），它不改变车辆或模块状态。
* 原始证据：`captures/commander/<UTC>.jsonl`（本地、gitignored）。

## 2. 密码闸门（首次发现，之前完全不知道）

模块对**数据类命令**（176/208/209/210）有密码闸门：

| 现象 | 证据 |
|---|---|
| 未握手时任何写入都只回 `168 ff`（= 需要密码）+ 一份 160，其中**数据体全为 0** | 第一次采集：160 载荷 `00101001 535ceae3 … 535c0000 0000…`（[4..15] UID 之后全 0） |
| 握手成功后同一支 160 变成有内容 | `00101031 535ceae3… 535c0040 32000105 0000ff010100000001090000 **31323334**`（末尾回显密码 ASCII "1234"，硬件版本字节从 0x00 变 0x31） |

握手格式从模块自带控制软件读出：**CMD 168 + 四位 ASCII 密码**
（`tx(168, [charCode×4])`），返回码 `255=需要密码 / 0=错误 / 1=正确`，
且客户端源码里 `"1234" == r` 是**不消耗尝试次数**的默认值（其余密码 3 次后锁 1 小时）。

本次只发一次默认握手，成功，未重试任何其他密码。

## 3. 160 — 模块身份（已解码）

| 偏移 | 值 | 说明 |
|---|---|---|
| `[0]` | `0x00`（握手后变 `0x31`） | 硬件版本字节；**本机未设置**，客户端平时从服务器取 hw_ver |
| `[1]` / `[2]` | `0x10` / `0x10` | bootloader / 固件（客户端左移 8 位 → 4096） |
| `[3]` | `0x01` | bit0 = 线束已插好 |
| `[4..15]` | 12 字节 UID | 客户端转 24 位 hex 作为设备 id |
| `[40]` | `0x01` | 走 VIN 分支 |
| `[41..57]` | 17 字节 ASCII VIN | 本机 VIN（`5YJ3E1EB…`，完整值只在本地证据文件里） |

结论：**160 的布局与客户端源码一致**（`s[40]==1 → VIN at [41..57]`），
本机载荷 76 字节（客户端另有 178 字节分支，属别的版本）。
硬件版本字节不能用来选布局——它是 0，客户端靠服务器补齐。

## 4. 176 — 仪表数据流：**是推送，不是轮询**

发一次 `176 [1]` 之后模块**连续推送**，无需重复请求：

| 指标 | 实测 |
|---|---|
| 帧数 / 时长 | 15 帧 / 6.0 s |
| 间隔中位数 | **0.421 s**（约 2.4 Hz） |
| 最小 / 最大间隔 | 0.059 s / 0.841 s |
| 停止 | `176 [0]` |

这直接解决了一项长期未知：**仪表侧不需要轮询，订阅一次即可**。
（之前的假设是"每秒轮询一次"，那是客户端为了刷新自己界面才那么写的。）

### 4.1 一个会害死人的字段标签错误（已修）

客户端把 `payload[4..7]` 的 bits 6-31（`/10`）标注为"剩余总里程"，但实机
同一秒里：

| 来源 | 值 |
|---|---|
| 176 该字段 | **211040.4** |
| 208 的总里程字段 | **211040.4**（完全一致） |
| 176 的 1.61× 字段 | **170.7 km** |
| 208 的剩余里程字段 | **170.7 km**（完全一致） |

所以该字段是**总里程（odometer）**，真正的剩余续航是 1.61× 那个字段。
我们此前的 `applyCommanderReadingsV6()` 把前者写进了 `range`——由于现在
指挥官优先于 MCU，这会让能量列显示 211040 km。**已修正**，并加了回归测试
（`tests/page_projection_tests.cpp`："the odometer field is not a range"）。

## 5. 208 — 电池包：真实 SOC 与容量（已解码）

一次请求回一条 29 字节摘要（本次 `[2]` 请求得到回应）：

| 项 | 解码值 |
|---|---|
| 包电压 | **361.80 V** |
| 包电流 | **+3.9 A** |
| 包功率 | **+1.41 kW** |
| 累计放电 / 充电 | 57688.5 / 57594.4 kWh |
| 剩余能量 | **27.66 kWh** |
| 满电容量 | **61.26 kWh** |
| 保留能量 | 2.76 kWh |
| 单体最高 / 最低 / 压差 | 3.774 / 3.772 V / **2 mV** |
| 剩余里程 | **170.7 km** |
| 电池温度 | **28.0 ℃** |
| 正在预热 | 否 |
| 总里程 | 211040.4 km |
| 车机 SOC（7 位） | **43 %** |
| **实际 SOC（能量比）** | **(27.66−2.76)/(61.26−2.76) = 42.56 %** |
| 出厂容量字段 | 1 → 0.1 kWh，**未设置**（客户端此时显示"设置"而不是数字） |

### 5.1 SOC 交叉核对

同一时刻模块给出两个独立来源：**车机 SOC 43 %** 与**能量比 42.56 %** ——
相差 0.5 %，互相印证。两者都远低于原车 MCU 那个恒读 97 % 的字节，进一步
确认 "MCU SOC 字节不可信、SOC 只认指挥官" 是正确策略。

**人工核对（2026-09-24，车主在车内）：中控屏显示的百分比与上述读数一致。**
这是第三次独立印证（模块能量比 / 模块车机 SOC / 整车中控屏），因此：

* `actual_soc` 的**来源**确定为指挥官，公式不变（没有为了凑相等而改过任何系数）；
* 原车 MCU 的 SOC 字节在本车上**确认不可用**，继续不参与仲裁；
* 单体电压也自洽：43 % 对应每串约 **3.77 V**（实测 3.772–3.774 V），
  与 NCA 三元锂在该电量区间的开路电压相符，说明 208/209 两套数据没有互相矛盾。

> 记录方式：只记录"中控屏一致"这一结论，不猜测具体数字；若以后出现明显
> 差异，同样只记录差异，不改公式。

## 6. 209 — 单体电压：**订阅后流式推送**

| 指标 | 实测 |
|---|---|
| 帧数 / 时长 | **771 帧 / 约 21 s**（约 37 Hz 的突发） |
| 载荷 | 8 字节：`[0]` 包序号、`[1]=0x2a`、`[2..7]` 三路小端 u16 ×1e-4 V |
| 覆盖 | 序号 **0..35** → 36 包 × 3 = **108 个单体位** |
| 有效 / 全零 | 683 帧有非零单体；88 帧全零（客户端把 0 视为无效） |
| 电压范围 | 约 **3.75-3.78 V**，与 208 的 3.772/3.774 V 一致 |

结论：**209 不是一次问答，而是请求后持续突发推送**；仪表侧订阅一次即可。
