## 1. 铰链枢轴（Part I1）

不是靠 bounding box 猜的，而是同时用三种方式验证：

```
door bbox   min=(-0.2329, 0.6607, 0.2357)  max=(1.0435, 1.0929, 1.3132)
door origin = (1.0406, 0.8982, 0.6151)
origin 到 bbox 前缘 = +0.0029 m   （门长 1.2764 m）
verdict: ON THE HINGE (front edge)
```

原点距门的前缘只有 **2.9 mm**，即在铰链轴上。

## 2. 旋转方向：上一轮的结论是错的

上一轮的交接记录写的是"已修正为 +Z 会把 +Y 侧的门向外转开"。**这个结论是错的**，
而且当时的验证方法本身不成立（见 §4）。

用世界坐标包围盒直接测量（`swing_direction_report`）：

```
closed:     y range 0.661..1.093
+Z 52 deg:  y range -0.252..1.020  | far-edge y delta -0.073 m -> INWARD (through the car) - WRONG
-Z 52 deg:  y range  0.750..2.022  | far-edge y delta +0.929 m -> OUTWARD (away from the car)
```

+Z 会把门**横穿车身**转到中心线另一侧（y 变成 −0.252，车体中心在 y≈0）。
正确的方向是 **−Z**，门的后缘向外推到 y=2.022。

脚本里现在把方向固定成常量 `OPEN_SIGN = -1.0`，并且 `--verify` 每次都会重新
打印这段测量，防止再被改回去。

## 3. 碰撞扫描（Part I2）

### 3.1 方法必须先修

第一版碰撞扫描比较的是门和车身的 **local 顶点**（`mesh.vertices`），而两个物体的
`matrix_world` 不同 —— 两个 BVH 根本不在同一个坐标系里，所以它在**每一个角度**
（包括 0°，此时门就贴在车身上）都返回 0 个重叠面。

现在两棵树都先转到世界坐标再建 BVH。

### 3.2 还要扣掉"出厂就重叠"的部分

MODEL A 的门板是塞在门洞里的，闭合时本来就和车身有 **964 个面**接触。这不是
动画造成的，必须当基线扣掉，否则任何角度都会被判成穿模。

### 3.3 结果（正确方向 −Z）

| 角度 | 重叠面对 | 新增车身面 | 可见外皮穿模 | 外缘行程 |
|---|---|---|---|---|
| 0° | 2380 | 0 | 0 | 0.000 m |
| 5° | 229 | 89 | 177 | 0.113 m |
| 10° | 326 | 274 | 321 | 0.226 m |
| 20° | 403 | 403 | 403 | 0.450 m |
| 30° | 422 | 422 | 422 | 0.671 m |
| **52°** | **~390** | **~390** | **~390** | **1.14 m** |
| 70° | 396 | 396 | 396 | 1.486 m |

关键点是**曲线形状**：一开门重叠就从 2380 掉到 229，之后 15°→70° 一直稳定在
380–420，**不随角度增长**。也就是说继续开大不会引入新的穿模；剩下的约 390 个
面是铰链侧门缝本来就贴在一起的部分。

因此 52° 判定为几何安全。真车的 Model 3 前门大约能开到 60–70°，52° 是为了在
仪表上读起来自然、同时保留 canvas 边距的选择。

## 4. 上一轮遗留的第三个缺陷：动画帧全是黑的

`render_door_animation.py` **完全没有创建任何光源**。它调用了 V2 材质和反射
摄影棚，但 `read_factory_settings(use_empty=True)` 已经把 world 删掉了，
场景里没有任何发光体（摄影棚卡片在 EEVEE 下不产生照明）。结果 9 组序列全部是
**纯黑剪影**：车体可见像素最大 RGB = **1**（0–255）。

修复：复用 `render_vehicle_visual_v2.setup_key_rig()`（3 点柔光灯 + world），
保证动画和静态图用**同一套光**。修复后平均亮度 79.5–80.2，最亮 229，与静态
渲染一致。

## 7. 动画可见性

相机在驾驶员侧（−32°）时，开门会改变 **12.1%** 的车体像素（0° → 52°）；
相机在副驾侧时会掉到 7.5%，门看起来只是"车后面有东西动了一下"。
这就是相机必须换边的定量理由，详见 `VEHICLE_VISUAL_V2.md` §2。

## 8. 不做整段 preload（Part L）

沿用之前的审计结论：`ZKImageAnim` 流式解码，**禁止**把整段动画的所有帧 RGBA
常驻内存。每个变体的 frame count / PNG 大小 / 解码体积 / 解码预算百分比见
`ANIMATION_PERFORMANCE_TEST_PLAN.md` 与 `tools/assets/check_budget.py`。

# V3 追加：运动打磨 + Open/Close 分离（Parts 10-11）

基线 `2f103e3`。几何 / 铰链 / 旋转方向全部保持 V2 的结论（已人工 PASS），
本轮只改**时长、easing、以及 open 与 close 的分离**。

## 11. Open / Close 是两段独立动画

Close **不是**运行时把 Open 倒放。两段各自有独立的时长与独立的 easing 函数，
并且分别渲染成两套序列。

| | 时长 | 帧数 @30fps | 帧数 @60fps | easing |
|---|---|---|---|---|
| **Open** | 0.62 s | 20 | 38 | `ease_in_out_cubic` |
| **Close** | 0.54 s | 17 | 33 | `ease_in_out_quint`（smootherstep） |

另外提供 **0.55 s** 的 Open 候选供人工比较：
`assets/rendered/door_fl_v3/600_30_open_055/open`（17 帧）。

### 11.1 为什么 Close 用另一条曲线

Open 是"松开锁扣 → 自然加速 → 接近全开时减速"，三次方 ease-in-out 就够。

Close 是要**贴合密封条停下**的运动：起点要有柔和的拉出感，终点要有阻尼感。
quintic smootherstep 在两端的速度**和**加速度都为零，读起来是"更重、阻尼更好"
的部件，而不是 Open 的镜像。两段都是严格单调且有界，
**无 spring、无 bounce、无 overshoot**。

角度曲线（由脚本里的函数直接算出，0.62 s / 30 fps，20 帧）：

| t | Open 角度 | t | Close 角度 |
|---|---|---|---|
| 0.00 | 0.0° | 0.00 | 52.0° |
| 0.25 | 3.2° | 0.25 | 46.6° |
| 0.50 | 26.0° | 0.50 | 26.0° |
| 0.75 | 48.8° | 0.75 | 5.4° |
| 1.00 | 52.0° | 1.00 | 0.0° |

两者在中点都恰好是 26°（这是对称函数的必然结果），但两端的曲率完全不同 ——
Open 在第 5 帧才到 3.8°，而 Close 在第 5 帧已经走完约 18% 的行程。
这就是"独立 easing"的实际含义。

完整角度序列：

```
open  (20 帧)  0.0 0.0 0.2 0.8 1.9 3.8 6.6 10.4 15.5 22.1
               29.9 36.5 41.6 45.4 48.2 50.1 51.2 51.8 52.0 52.0
close (17 帧)  52.0 51.9 51.2 49.5 46.6 42.6 37.7 32.0 26.0
               20.0 14.3 9.4 5.4 2.5 0.8 0.1 0.0
```

（Open 的首两帧都是 0.0°，这是"起步稍慢"在离散采样上的表现；
如果需要更早出现可见位移，应当改曲线而不是加长时长。）
