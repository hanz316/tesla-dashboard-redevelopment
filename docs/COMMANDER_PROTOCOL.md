## 2. 传输层

| 项目 | 值 |
|---|---|
| 服务 UUID | `0000FFF0-0000-1000-8000-00805F9B34FB` |
| 特征 UUID | `0000FFF1-0000-1000-8000-00805F9B34FB` |
| 特征属性 | notify + write（若支持 writeNoResponse 则优先用它） |
| 分包 | 发送前按 `MTU-3` 切片；默认 MTU 20（即 17 字节/包），Android 主动请求 247 |

## 3. 帧格式

```text
55 7F CMD LEN_HI LEN_LO DATA... CHK
```

| 字段 | 说明 |
|---|---|
| `55 7F` | 固定帧头（2 字节） |
| `CMD` | 命令号（1 字节） |
| `LEN_HI LEN_LO` | 数据长度，**大端** 16 位（0 表示无数据） |
| `DATA` | 载荷 |
| `CHK` | **从 CMD 开始**、含两个长度字节和全部 DATA 求和，取低 8 位（不是取反） |

接收端另有约束：长度 `0` 合法；长度 `> 4096` 视为错误并丢弃。

发送示例（源码 `tx()` 的实际算法）：`CMD=176, DATA=[1]` →
`CHK = (176 + 0x00 + 0x01 + 0x01) & 0xFF = 0xA2` →
`55 7F B0 00 01 01 A2`。

## 5. 状态回包：命令 160 / 161 / 163

回包长度至少 18 字节，另外**只有 `payload[3] & 1` 为真时模块才会继续发完整
状态**（客户端用它判断"线束是否插好"）。

| 偏移 | 含义 |
|---|---|
| `[0]` | 硬件版本号（决定后面用哪套布局） |
| `[1]` / `[2]` | bootloader 版本 / 运行固件版本 |
| `[3]` | 标志位，bit0 = 已插好 |
| `[4..15]` | 模块 UID（12 字节，客户端转成 hex） |
| `[46..62]` 或 `[41..57]` | VIN（ASCII，长度 178 或标记位决定） |

按硬件版本分支：

| 硬件版本 | 布局 |
|---|---|
| 3 / 5 / 6 / 7 / 8 / 19 | `[18]` AP 恢复状态、`[19]` 状态位图、`[20..21]` 运行时间（小端 /1000 秒）、`[22]` dat0、`[23]` dat1 |
| 4 / 10 | `[19]` 充电状态、`[20..21]` 电池电压（小端 /1000 V） |
| 9 | `[18]` 氛围灯亮度（>100 截断到 100）、`[20..22]` RGB 三字节 |

状态位图 `[19]`：`bit0` = 运行中；`bit7` = **线束未插好**。
`dat0`：`bit0-4` = 车辆类型；`bit7` = 车辆类型识别状态。
`dat1`：`bit0/1/2` = CAN1/2/3 已连接（仅硬件 6/7/8/19 有效）。

## 6. 数据回包

### 6.1 命令 176：仪表盘数据流

客户端在横屏仪表页里每 **1 秒**发一次 `176 [1]`，离开页面发 `176 [0]`。
回包长度 ≥ 33 才有扩展字段。

先按小端读 32 位 `first = payload[0..3]`：

| 位 | 含义 | 说明 |
|---|---|---|
| 0-8 | 车速 | 0-511 |
| 9-11 | 档位 | **1=P 2=R 3=N 4=D**，与 `Gear` 枚举一致 |
| 12-13 | 转向灯 | bit0 左、bit1 右 |
| 14-15 | AP 状态 | 0 关 / 1 / 2 / 3（客户端用蓝/绿/灰配色，语义未写明） |
| 16-19 | 车门位 | **bit0 主驾、bit1 左后、bit2 副驾、bit3 右后**（不是顺序的） |
| 20-23 + 27 + `payload[4]` bit1 | 灯光位 | 见下 |
| 24-30 | 车机 SOC | 0-100（7 位） |

灯光位（客户端图标对应关系）：`bit0` 远光、`bit1` 近光、`bit2` 示宽、
`bit5` 刹车。`light bit4` 与 `bit4`（由 `payload[4]` bit1 映射而来）两个
图标客户端有画但代码未写含义，**保持未命名**。

再按小端读 `second = payload[4..7]`：

| 位 | 含义 |
|---|---|
| 0 | `0` = 请求保持亮屏 |
| 1 | 前备箱打开 |
| 2 | 深色外观 |
| 3 | 运动模式 |
| 5 | 后备箱打开 |
| 6-31 | 剩余总里程，`/10` km |

`payload[8..11]` 四个胎压：`值 × 0.025 bar`；**`0` 和 `255` 表示无读数**
（不是 0 bar）。顺序按客户端画法为左前、右前、左后、右后（客户端只按
`Pressure[0..3]` 显示，未标注物理轮位，故仍是"顺序未确认"）。

`payload[12..15]`：

| 位 | 含义 |
|---|---|
| 0-7 | 加速踏板：`round(100 × 值 / 250)`，上限 100 % |
| 8-18 | 后电机功率：**有符号 11 位** `/2` kW |
| 19-29 | 前电机功率：有符号 11 位 `/2` kW |

`payload[15..17]`（长度 ≥ 33 时）：海拔 = 有符号 14 位（从 bit6 起）米；
`payload[17]` bit4-5 = 电池预热状态、bit6 = 英制单位、bit7 = 方向盘手握检测。

`payload[18..22]`：四个刹车盘温度，各 10 位，`- 40` ℃（第 4 个跨到
`payload[22]` 的 bit0-1）。

`payload[23..26]`：鼓风机 `5 × (bit0-9)` RPM；蒸发器需求 `5 × (bit10-20)` W；
座舱温度 `0.1 × (bit21-31) - 40` ℃。

`payload[27]`：环境温度 `0.5 × 值 - 40` ℃。

`payload[28..31]`：电芯电压 `0.002 × (bit0-11)` V；剩余里程
`1.61 × (bit12-21)` km；电池温度 `0.5 × (bit22-30) - 40` ℃。

`payload[31..32]`：限速 `5 × (bit7-11)` km/h，**只在 R/N/D 档显示**
（客户端在 P 档显示 0）；后向盲区左右各 2 位等级。

### 6.2 命令 208：电池包概要

| 偏移 | 含义 |
|---|---|
| `[0..1]` | 总电压 `×0.01` V |
| `[2..3]` | 总电流 `×-0.1` A（源码对 < -3276.7 A 再加 6553.6 的一次回绕修正） |
| 计算 | 总功率 = 电压 × 电流 / 1000 kW |
| `[4..7]` | 总放电量 `×0.001` kWh |
| `[8..11]` | 总充电量 `×0.001` kWh |
| `[12..15]` bit0-15 | 剩余电量 `×0.02` kWh |
| `[12..15]` bit16-31 | 出厂容量 `×0.02` kWh |
| `[16..17]` | 保留电量 `×0.01` kWh |
| `[18..20]` bit0-11 / bit12-23 | 单体最高 / 最低 `×0.002` V |
| `[21..24]` bit0-9 | 出厂容量 `×0.1` kWh |
| `[21..24]` bit10-19 | 剩余里程 `×1.61` km |
| `[21..24]` bit20-21 | bit20-21 == 2 表示正在预热 |
| `[21..24]` bit22-30 | 电池温度 `×0.5 - 40` ℃ |
| `[24..25]` bit7-13 | **车机 SOC**（7 位） |
| `[25..28]` bit6-31 | 总里程 `÷10` km |

**实际 SOC** 由客户端自己算：

```text
可用 = 出厂容量 - 保留电量
实际SOC = (剩余电量 - 保留电量) / 可用 × 100%     # 剩余电量为 0 时退回车机 SOC
```

两个反直觉之处，实现时必须照做：

1. **`payload[24]` 是共用字节**：低 7 位属于温度/容量字（bit24-30），
   bit7 属于车机 SOC 的第 0 位（`(payload[25]<<8 | payload[24]) >>> 7`）。
   把这两个字段当成互不相干的字节就会两个都错。
2. `payload[25]` 同时承载车机 SOC 的高 7 位和总里程的低 2 位。

### 6.3 命令 209 / 210

| CMD | 布局 |
|---|---|
| 209 | `payload[0]` = 起始串号/3；`payload[2..7]` 每 2 字节小端 `×1e-4` V 为一个单体电压（一条消息 3 个），为 0 视为无效；客户端据此求最大/最小/平均/压差 |
| 210 | `[0..3]` bit16-31 输入电压 `×0.1` V、bit0-15 输出电压 `×0.01` V；`[4..7]` bit0-15 输出电流 `×0.1` A；输出功率 = 输出电压 × 输出电流 |

电池页轮询方式：进入页面发 `208 [1]`，之后每 500 ms（单体页 1 s）发
`208 [select+2]`，离开发 `208 [0]`。

## 8. 仪表侧怎么用（已实现）

```text
手机/仪表收到的字节 ──► CommanderFrameReaderV6 ──► 按 CMD 分派
                                                  ├─ 160 → CommanderDeviceInfoV6
                                                  ├─ 176 → CommanderGaugeV6
                                                  ├─ 208 → CommanderPackV6
                                                  └─ 210 → CommanderDcdcV6
                                                          │
                                    applyCommanderReadingsV6() ─► VehicleState（只写增强字段）
```

规则：

* **速度、档位、续航、MCU 的 SOC 字节、车门、灯光、胎压仍然来自原车
  MCU 直读路径**，指挥官即便也报了这些值也不覆盖（`applyCommanderReadingsV6`
  里根本没有写这些字段）。
* 若将来要用指挥官兜底这些直读信号，必须显式调用
  `applyCommanderFallbackV6()` 并逐项打开开关，且质量标记为 `Inferred`。
* `actual_soc` 取模块算出的**实际 SOC**；模块算不出时退回它报的**车机
  SOC**（标记 `Inferred`）。**任何情况下都不用 MCU 的 SOC 字节**。
* `NAN`/无读数一律保持无效：胎压 `0/255`、单体 0、剩余电量为 0 时都不会
  被写成 0 值。

对应实现：`include/dashboard/commander_link.h`、`src/core/commander_link.cpp`，
测试在 `tests/page_projection_tests.cpp`（用真实位布局构造 176/208 帧，
并逐条断言控制命令不可发送）。

## 10. 仪表怎么自动连上模块

先说结论：**自动连接的两条路都已经定下来，逻辑部分已经写完并有测试；
剩下要选的是走哪条传输。**

### 10.1 传输无关的部分（已实现）

```text
启用模块 ──► schedule.shouldAttempt() ──► 传输尝试连接
                ▲                              │
                │ 失败：1s→2s→4s…封顶 30s        │ 成功
                └──────────────────────────────┘
                │ 已连上但 3 s 没帧 → Stale → 立刻按 1 s 重试
```

* `CommanderConnectScheduleV6`：退避、封顶、连上清零、静默立刻重试。
* `CommanderBridgeV6`：把收到的字节送进 `CommanderFrameReaderV6`，维护
  `CommanderLink` 状态、解码结果与连接计划，`tick()` 负责老化。
* 这两者与传输完全解耦：换 BLE、换 Wi-Fi、换串口都不需要改它们。

测试：`tests/commander_bridge_tests.cpp`（退避曲线、静默→Stale→重试、
真实 loopback UDP 收发、跨数据报的半帧重组）。

### 10.2 路 A：手机转发（PhoneBridge）—— 现在就能做

模块本来就是靠手机小程序控制的，小程序**已经是**这台模块的 BLE Central
（服务 FFF0 / 特征 FFF1，带 notify）。所以最短路径是：

```text
模块 ──BLE──► 手机（小程序/独立 App，保持连接与自动重连）
                  └── Wi-Fi/UDP ──► 仪表 CommanderUdpListenerV6 ──► 解码链
```

仪表侧已经实现：`CommanderUdpListenerV6` 绑定一个 UDP 端口（设备上绑
`0.0.0.0`，测试绑 loopback），**只收不发**——没有发送路径，就不可能变成
第二条控制通道。收到什么就喂给同一个 reader，跨数据报的半帧会自动重组。

手机侧要做的改动很小：连接成功后把 notify 回调里收到的 `Uint8Array` 原样
`wx.sendSocketMessage`/UDP 发出去即可；断线重连用小程序已有的机制。

### 10.3 路 B：仪表直连模块 —— 能力在，接口没开放

对仪表固件与平台自带蓝牙守护进程 `blink` 的实测结论：

| 事实 | 证据 |
|---|---|
| `blink` 里有完整 LE 扫描与建连 | 二进制含 `hci_le_create_connection`、`hci_le_set_scan_parameters`、`hci_le_add_device_to_white_list` |
| `blink` 里有 GATT 客户端 | 含 `ON_BLINK_GATT_SEARCH_START/STOP`、`GATT_CHARACTERISTIC_VALUE_QUERY_RESULT`、`GATT_NOTIFICATION/INDICATION`、`[BLE: browser] ... characteristic uuid` |
| 应用侧与 `blink` 的通道 | `/dev/BT_serial`（pty），文本命令，日志形如 `----CMD: [%s]----`、`The CMD Is Not Find (%-6s)` |
| 应用层 SDK | `libzkhardware.so` 里没有 BLE/GATT 符号；stock 应用的 `bt::` 只暴露经典协议 |
| 平台无 BlueZ | 无 `bluetoothd`/hcitool/gatttool 可用 |

结论：**不是"没有能力"，而是"没有公开的开箱接口"**。要让仪表自己连，需要
在平台侧做一件事（任一）：

1. 用 `/dev/BT_serial` 的命令通道驱动 `blink` 的 LE/GATT（需要把命令词表
   摸清，例如 `ON_BLINK_CONNECT_DEVICE`、`BLINK_CONNECT_DEVICE`、
   `ON_BLINK_GATT_SEARCH_START`，以及 characteristic 读写/订阅命令）；
2. 让厂商在 SDK 里开放通用 GATT client API（正路，但要厂商配合）；
3. 自行接管 BT 串口（`/dev/ttyS3`）/HCI——风险最高，会和 `blink` 抢控制器，
   不建议。

这条路需要真机联调，属于平台工程；在它完成之前，路 A 完全够用。

### 10.4 建议

先用 **路 A** 把整条链路和九个屏幕跑通（不需要任何平台改动，仪表侧代码
已经就绪）；等平台侧愿意开放 GATT 或确认 `blink` 命令词表后，再换成
**路 B** 让仪表自己连。两条路共用同一份帧解析、仲裁与 UI，换的时候只换
传输。
